# Summary: Configurable project setup (`mcp-coder setup`) — issue #1204

## Goal

Every repo declares how it is set up in `[tool.mcp-coder.setup]`. One command,
`mcp-coder setup --project-dir <dir> [--refresh] [--skip-overrides]`, runs those
steps the same way on Windows, macOS and Linux. Every launcher (vscodeclaude
session, Linux Jenkins templates, CI job, later AutoRunner#59) calls only that
command, so future setup changes land in mcp-coder alone.

Python repos without the table keep today's behaviour through the default
`[{ builtin = "python" }]` (= today's `mcp-coder install --source local
--use-sync`, run in-process). `mcp-coder install` itself is unchanged.

## Architectural / design changes

| Area | Change |
|---|---|
| Config | New `[tool.mcp-coder.setup]` table, `steps` = ordered list of `{argv \| builtin, name, timeout}`. Read from `pyproject.toml`, else root `mcp-coder.toml`, per table (toolkit and setup may live in different files). Strict loading. |
| Two-file lookup | Extracted from `load_toolkit_config` into one helper in `utils/toml_utils.py` that takes the table name; the toolkit and setup loaders both use it. |
| `argv[0]` resolution | One resolver `utils/executable.py:resolve_executable`, shared by the command toolkit, `mcp-coder setup` and `verify`. Own Windows rules (`PATHEXT` variants, no extensionless fallback, `PATH` only for bare names, never cwd) without `shutil.which`, so the rules are unit-testable on Linux. The command toolkit's `_resolve_exe` is removed. |
| Step runner | New module `mcp_coder/install/project_setup.py` (inside the existing `install` package — no new package, no new import-linter contracts). Runs steps in order, stops at the first failure. Built-in `python` calls `install()` in-process; later steps get the project venv's bin dir first on `PATH` and `VIRTUAL_ENV`. Sets `UV_GIT_SHALLOW=0` unless already set. Fails when setup changed tracked files or created untracked, non-ignored files. |
| Layering | `tach.toml`: `mcp_coder.install` gains `mcp_coder.mcp_workspace_git` in `depends_on` (changed-files check). Import-linter layers already allow it (`install` > `utils` > `mcp_workspace_git`). Core still never imports `mcp_coder.toolkits`: the resolver lives in `utils`. |
| CLI | New `setup` command (SETUP category). |
| `verify` | New `Setup` row in PROJECT, in its own module `cli/commands/verify_setup.py`; loads the config strictly and resolves every `argv[0]`, runs nothing. |
| Session launcher | Calls `mcp-coder setup` instead of `install`. Setup env = today's env without the project venv overlay and without an inherited `VIRTUAL_ENV`. The session env is built **after** setup; `VIRTUAL_ENV` + `PATH` prepend only when `<repo>/.venv` has an interpreter. `MCP_CODER_VENV_DIR` now always names the tool env. `validate_target_repo` gives Python warnings only when the steps include the `python` built-in. |
| Linux templates | implement, fix-ci, fix-conflict, review-implementation run `mcp-coder setup` after `git pull` (failure → watchdog `set-status`, `exit 1`), then set `VIRTUAL_ENV` when `.venv/bin/python` is executable. The four templates are generated by one helper, so the watchdog line exists once. Test template activates `.venv` only if it exists. Windows templates unchanged. |
| Tests | New `setup_integration` marker (npm, Rust, Python fixtures generated into `tmp_path`). |

Design rules applied (KISS):
- No new package: the runner sits next to `install()` which it calls.
- Built-in names are validated by the loader; the runner holds a plain dict `{"python": _run_python_builtin}`.
- The `python` built-in builds an `argparse.Namespace` and reuses `InstallConfig.from_args`, so extras / `post_install_checks` resolution is not duplicated and `install` stays untouched.
- Env overlays go through `CommandOptions.env`, which `prepare_env` merges over `os.environ`.
- "Venv has an interpreter" is one helper `venv_python()` built on `mcp_verification.get_bin_dir` (no new bin-dir helper).

## Steps

1. Shared `argv[0]` resolver; command toolkit uses it.
2. Shared two-file table lookup and setup config loader.
3. Setup step runner in `install/project_setup.py`.
4. `mcp-coder setup` CLI command.
5. `setup_integration` tests and marker registration.
6. `verify` `Setup` row.
7. Session launcher calls `mcp-coder setup`; env built after setup; CI job.
8. `validate_target_repo` gates Python warnings on the `python` built-in.
9. Linux Jenkins templates run `mcp-coder setup`.
10. Documentation.

Each step is one commit. Before committing: `run_format_code`, then pylint, pytest (unit marker filter from `.claude/CLAUDE.md`, `-n auto`), mypy, lint-imports, tach must pass. If a precondition named in a step does not hold, write one line to `pr_info/.blocked.txt` and stop.
