# Decisions — I3.1 feasibility spike (#1044)

Decisions taken while refining the step plan. Each entry records what was decided and why.

## Plan review round 1 (log 2), accepted by tech lead

All eight arose from the round-1 plan review recorded in `pr_info/plan_review_log_2.md` and were
approved by the tech lead. They change the plan only — no production code, no CI/`pyproject.toml`
changes (D8 stays confirm-only; the review confirmed no requirement changes are needed).

| ID | Decision | Rationale | Applied in |

| **F1** | The D5 registry probe resolver takes `resolve_from_thread(loop, registry, approval_id, decision)` and does the `registry[approval_id]` → future lookup **inside the thread**, before `call_soon_threadsafe`. Reverse-order ordering and distinct-decision assertions unchanged. | Passing the `Future` object directly bypasses the registry, so the reverse-order scenario only proved "two independent Futures resolve independently" — it would pass green against a completely cross-wired registry, exactly the hazard D5 exists to catch. ## Plan review round 2 (log 2), accepted by tech lead

All six arose from the round-2 plan review recorded in `pr_info/plan_review_log_2.md` and were
approved by the tech lead. They change the plan only — no production code, no CI/`pyproject.toml`
changes (D8 stays confirm-only; two review rounds have now confirmed no requirement changes are
needed). Nothing settled in F1–F8 or D1–D10 is re-opened.

| ID | Decision | Rationale | Applied in |
|----|----------|-----------|------------|
| **F9** | The shared `FakeChatModel` implements the **async** method `async def _agenerate(self, messages, stop=None, run_manager=None, **kw) -> ChatResult`, recording `loop_id` and `messages` there. `_generate` may stay unimplemented/raising. The class docstring is updated to match. | `langchain_core.BaseChatModel`'s default `_agenerate` delegates to `run_in_executor(None, self._generate, ...)`, so a model implementing only `_generate` runs on a **thread-pool thread with no running loop**, where `asyncio.get_running_loop()` raises `RuntimeError`. That destroys `model.loop_id` — the *independent* agent-loop reference `step_5.md` compares `gate.loop_id` against, and on which `step_6.md` §1 gates the entire positive go/no-go verdict. | `step_2.md` |
| **F10** | `run_bridge` gains explicit `inactivity_timeout: float = 300.0` and `overall_cap: float = 3600.0` parameters (defaults matching production), and `BridgeRun` gains `error: BaseException | None` capturing what the copied consumer raised on the worker thread. Step 3's `scenario_baseline_dies` then just names the values it passes and asserts `isinstance(run.error, TimeoutError)`. | `scenario_baseline_dies` (F5) was unwritable as specified: (a) `run_bridge` had no timeout parameters, so the negative control could not run under `INACTIVITY_TIMEOUT=2.0` / `OVERALL_CAP=3.0`, and Step 2's `scenario_inert` needs a *long* inactivity timeout (its tool never resolves), so a hardcoded short value would break Step 2; (b) `BridgeRun` had no error channel — the consumer generator runs on a worker thread, so the `TimeoutError` the negative control must assert never reached the main thread. | `step_2.md`, `step_3.md` |
| **F11** | `BridgeRun.close()` while the consumer is blocked is documented as raising `ValueError: generator already executing`, and `scenario_inert` asserts *that* as the demonstration. `step_6.md` §4 wording changes from "`GeneratorExit` is inert" to "`GeneratorExit` is **unreachable** while blocked — the only thread that could close the generator is the one stuck inside `next()`". No structural change. | CPython refuses `gen.close()` while the generator frame is executing, and the worker thread sitting in `q.get(...)` *is* executing it — so `close()` does not deliver `GeneratorExit` at all. This is a stronger fact than the plan claimed. | `step_2.md`, `step_6.md` |
| **F12** | `FakeChatModel` takes a constructor script: `FakeChatModel(responses: list[AIMessage] | None = None)`, invoke N returning `responses[N-1]`. The default is the 2-entry script Steps 3 and 5 use (tool_call → `'done'`); `scenario_backstop` passes its own 3-entry script (tool_call(blocking) → tool_call(instant) → `'done'`). | The plan said "Configure `FakeChatModel` to …" as if a knob existed, but the signature block had none, so `scenario_backstop` contradicted the shared fake's documented 2-invoke script. The script *is* the configuration; scenarios do not collide because each constructs its own model. | `step_2.md` |
| **F13** | The deny-`tool_call_id` check becomes a **recorded probe, not a gating assert** — print `PASS: deny-tool-call-id-filled` when it holds, `OBSERVED: deny-tool-call-id-empty (finding for I3.2 / latent I2.3 bug)` when it does not, exiting 0 either way. Step 5's DoD states this exception explicitly; `step_6.md` §10 records whichever outcome occurred. Every **other** Step 5 assertion stays gating. | Step 5's DoD ("exits 0, all PASS lines") conflicted with `step_6.md` §10 calling a negative outcome a valid recorded finding — the run cannot both fail and be the deliverable. It is not hypothetical: `langchain_core.BaseTool._format_output` returns `ToolOutputMixin` instances unchanged and `ToolMessage` **is** a `ToolOutputMixin`, so the empty id may well survive `ToolNode`. Matches §10.3's "demonstrated working **or** documented-impossible with rationale". | `step_5.md`, `step_6.md` |
| **F14** | Tier C's `Gate` is renamed `InterceptorGate` and the "never import `*`" warning comment is dropped; the declaration gains the missing `loop: asyncio.AbstractEventLoop | None` and `future: asyncio.Future[str] | None` fields. | Two unrelated classes named `Gate` (`_common.Gate`, the cross-thread handoff, and `tier_c.Gate`, the interceptor hook) collided; renaming removes the hazard rather than documenting it. `step_5.md`'s resolver thread must approve "the pending Future", but the class declared only `fired` / `loop_id` — there was nothing for `call_soon_threadsafe` to target. | `step_5.md` |
